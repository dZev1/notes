## Ejercicio 1

Un proceso será el encargado de completar los valores de un arreglo de enteros de **M** posiciones con valores específicos.
Para ello va a crear **N** procesos hijos, quienes cuentan con la función `int generarValor (int indice)`,
que toma como argumento el índice del arreglo que queremos completar, y devuelve un número entero.
Esta función sólo puede ser ejecutada en el contexto de procesos hijos.

Por último, cuando el padre tenga el arreglo de **M** posiciones completo y sus hijos hayan terminado, deberá informar su valor utilizando la función
`printArray(int[] array)`. Se pide:

a) Escribir el pseudocódigo de un programa que cumpla con lo solicitado,
utilizando pipes como medio de comunicación entre procesos, asumiendo que **M es múltiplo de N** y que los hijos trabajan de manera equitativa.

b) Supongamos que `generarValor()` puede demorar un tiempo variable en cada caso, por lo que algunos procesos pueden terminar su trabajo antes que otros, y queremos que no haya procesos hijos ociosos en caso de que aún queden tiems del arreglo sin procesar. ¿La solución provista en el inciso anterior funciona? En caso afirmativo, justificar. En caso negativo, explicar por qué y proponer una idea de solución.

### 1.A

```c

void run_child(int pipe[2], int M, int N, int id) {
    close(pipe[READ]);
    int value;

    for (int i = id; i < M; i += N) {
        value = generarValor(i);
        write(pipe[WRITE], &value, sizeof(value));
    }

    close(pipe[WRITE]);
    exit(EXIT_SUCCESS);
}

int main(int argc, char *argv) {
    if (argc != 3) exit(EXIT_FAILURE);

    int N = atoi(argv[1]);
    int M = atoi(argv[2]);

    int array[M];
    int pipes[N][2];

    for (int i = 0; i < N; i++) {
        pipe(pipes[i]);
        if (fork() == 0) {
            for (int j = 0; j < i; j++) {
                close(pipes[j][READ]);
                close(pipes[j][WRITE]);
            }
            run_child(pipes[i], M, N, i);
        }
    }

    for (int i = 0; i < N; i++) {
        close(pipes[i][WRITE]);
    }

    int temp;
    for (int i = 0; i < M; i++) {
        read(pipes[i % N][READ], &temp, sizeof(temp));
        array[i] = temp;
    }

    for (int i = 0; i < N; i++) {
        close(pipes[i][READ]);
        wait(NULL);
    }

    printArray(array);
    return EXIT_SUCCESS;
}
```

### 1.B

La solución provista no deja ningún proceso oscioso, pues apenas termine de generar todos sus respectivos valores, el proceso termina, y por lo tanto no queda como proceso zombie u ocioso.

> [!note]
> No es así, lo que se buscaba era algo del tipo que todos los hijos procesen la mayor cantidad de índices que puedan.
> Para eso podíamos utilizar solamente 2 pipes, uno de padre a hijo para indicar los índices que restan, y otro para enviar los resultados de hijo a padre.
> Entonces de esta manera, los indices se generan on-demand, en vez de manera prefijada.

## Ejercicio 2

Tenemos un sistema donde existen dos tipos de procesos:

- **Proceso Tipo 1:** Recibe una solicitud de un usuario y agrega un trabajo a una cola de tareas. Esta cola tiene tamaño máximo **N**, ya que no se pueden tener demasiadas tareas en memoria.
- **Proceso Tipo 2:** Toma trabajos de la cola (usando `pop()`) y realiza un trabajo de procesamiento.

Si la cola se llena, no se le deben agregar nuevos trabajos. **La cola de trabajos no es atómica**. La interacción de cada proceso con la cola se implementó hace poco y su comportamiento se puede representar con el siguiente pseudocódigo:

```c
// memoria compartida
mutex = sem_init(1);
jobs = sem_init(0);
buffer cola(N);

proc_tipo1() {
    trabajo = esperarPromptUsuario();
    mutex.wait();
    cola.add(trabajo);
    mutex.signal();
    jobs.signal();
}

proc_tipo2() {
    mutex.wait();
    jobs.wait();
    trabajo = cola.pop();
    mutex.signal();
    enviarResultado(trabajo);
}
```

Sin embargo, se reportó que esta parte del código no está funcionando correctamente y que no cumple exactamente con lo pedido. Nos encargaron la tarea de identificar qué está ocurriendo. Se pide:

a) Encontrar qué problema/s tiene este código con respecto a la sincronización de los procesos. Justificar detalladamente la/s causa/s y corregirlo, cumpliendo con la consigna del problema.

b) Ahora se desea que $k$ procesos Tipo 2 (con $k$ mucho menor que **N**) trabajen concurrentemente, pero sólo puedan enviar un resultado cuando $k$ procesos hayan extraído una tarea de la cola. Es decir, ningún proceso puede enviar el resultado inmediatamente después de retirar el trabajo de la cola, debe esperar a los otros procesos. Extender la solución del inciso anterior con esta restricción, asegurando que no haya problemas de concurrencia. Justificar la solución.

### 2.A

- Hay un problema en el orden del mutex y la cola de trabajos con su wait en el proceso tipo 2. Supogamos que primero se ejecuta el proceso tipo 2, hace `mutex.wait`, luego `jobs.wait`, y se queda colgado, sin haber hecho signal en el mutex, por lo que el proceso tipo 1 no va a poder encolar un trabajo, pues el mutex está ocupado.
- Otro problema ocurre en el hecho de que con esa implementación, podemos tener más signals en jobs que N, pues no estamos haciendo un checkeo de si efectivamente se agregó un elemento en la cola o no, llevando a problemas de `waits` y `signals` en el futuro.

Para arreglar esto, propongo lo siguiente, suponiendo que `cola.add` da 0 si no pudo agregar el elemento a la cola, y 1 si lo pudo agregar:

```c
mutex = sem_init(1);
jobs = sem_init(0);
buffer cola(N);

proc_tipo1() {
    trabajo = esperarPromptUsuario();
    mutex.wait();
    if (cola.add(trabajo))
        jobs.signal();
    mutex.signal();
}

proc_tipo2() {
    jobs.wait();
    mutex.wait();
    trabajo = cola.pop();
    mutex.signal();
    enviarResultado(trabajo);
}
```

### 2.B

Para implementar esto, hacemos un patrón Turnstile, para tener una barrera que no envie los resultados, hasta que k trabajos hayan terminado.

```c
mutex = sem_init(1);
jobs = sem_init(0);
turnstile = sem_init(0);
trabajos_terminados = 0;
buffer cola(N);


proc_tipo1() {
    trabajo = esperarPromptUsuario();
    mutex.wait();
    if (cola.add(trabajo))
        jobs.signal();
    mutex.signal();
}

proc_tipo2() {
    jobs.wait();

    mutex.wait();
    trabajo = cola.pop();
    trabajos_terminados++;

    if (trabajos_terminados == k) {
        trabajos_terminados = 0;
        turnstile.signal();
    }
    mutex.signal();

    turnstile.wait();
    turnstile.signal();

    enviarResultado(trabajo);
}
```

Como el incremento a trabajos_terminados ocurre dentro del mutex, asi como también el checkeo de ser igual a k, no hay problemas de race conditions con respecto a la variable trabajos_terminados, pues solo se maneja en la sección crítica.
