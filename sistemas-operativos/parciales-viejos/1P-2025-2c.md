## Ejercicio 1

Considerar el siguiente fragmento de código: 

```c
int ticket = 0;
int turno = 0;

void proc() {
	cosas_no_criticas();
	int miTurno = obtenerTurno();
	
	while (miTurno != turno) {}
	
	funcion_critica(); // sección crítica
	terminarTurno();
	cosas_no_criticas();
}
```

Dadas las siguientes implementaciones de las funciones `obtenerTurno` y `terminarTurno`:

```c
obtenerTurno() {
	int temp = ticket;
	ticket++;
	return temp;
}

terminarTurno() {
	turno++;
}
```

Responder:

a) Si dos procesos ejecutan este código de manera concurrente, determinar si al utilizar las funciones ob- tenerTurno y terminarTurno se delimita correctamente una sección crítica. En caso contrario, mostrar una traza que ejemplifique el problema. Justificar.

b) Si hay un problema con la exclusión mutua, ¿cómo sese podría arreglar? Justificar cómo y con qué meca- nismos de software/hardware.

### 1.A

No se delimita correctamente en esas funciones la sección crítica. Pongamos por ejemplo la siguiente traza:

| P1                       | P2                       | MEMORIA COMPARTIDA    | MEMORIA P1      | MEMORIA P2      |
| :----------------------- | :----------------------- | :-------------------- | :-------------- | :-------------- |
| cosas_no_criticas()      |                          | ticket = 0; turno = 0 |                 |                 |
| temp = ticket            |                          | =                     | temp = 0        |                 |
|                          | cosas_no_criticas()      | =                     | temp = 0        |                 |
|                          | temp = ticket            | =                     | **temp = 0**    | **temp = 0**    |
|                          | ticket++                 | ticket = 1; turno = 0 | =               | =               |
|                          | return temp              | =                     | =               | =               |
|                          | while (miTurno != turno) | ticket = 1; turno = 0 | =               | miTurno = 0     |
|                          | **funcion_crítica()**    |                       | temp = 0        | miTurno = 0     |
| ticket++                 |                          | ticket = 2; turno = 0 | temp = 0        | miTurno = 0     |
| return temp              |                          |                       | temp = 0        | miTurno = 0     |
| while (miTurno != turno) |                          |                       | **miTurno = 0** | **miTurno = 0** |
| **función_crítica()**    |                          |                       | miTurno = 0     | miTurno = 0     |

Como se observa en la traza, hay dos procesos que están en la zona crítica a la vez, esto debido a una race condition que viene desde la llamada a `obtener_turno()` que hace que los turnos no se guarden correctamente. De esta manera podemos llegar a tener turnos duplicados, como en la traza, debido a la inserción de la variable `temp` por fuera de una sección crítica de exclusión mutua, donde si cambia la memoria compartida pasan efectos no deseados.

### 1.B

Hay un problema con la exclusión mutua, para arreglarlo, usemos un mutex para delimitar las zonas críticas que requieran exclusión mutua, de la siguiente manera.

```c
int ticket = 0;
int turno = 0;

sem_t mutex = semaphore(1);

void proc() {
	cosas_no_criticas();
	
	mutex.wait();
	int miTurno = obtener_turno();
	mutex.signal();
	
	while (miTurno != turno) {}
	
	funcion_critica();
	
	terminar_turno();
	
	cosas_no_criticas();
}
```

Aplicando este mutex, las funciones que accedan a memoria compartida tienen garantizada la exclusión mutua para operar sobre esas variables, sin que haya efectos secundarios no deseados.

Otra manera de hacer esto, del lado del hardware, es usar `atomic ints`. Estos operan a nivel atómico, es decir, que no se puede cortar la ejecución en medio de una instrucción, sino que solo se puede una vez terminada la ejecución de esa instrucción. Entonces, podemos hacer algo de la siguiente forma:

```c
atomic int ticket = 0;
atomic int turno = 0;

obtenerTurno() {
	return ticket++; // devuelve el valor previo y luego lo incrementa
}

terminarTurno() {
	turno++;
}
```

y dejamos el resto como estaba. Ahora obtener turno funciona correctamente, y por lo tanto todo el resto de código, pues el problema venía del sistema de turnos previamente implementado.

## Ejercicio 2

Sea un sistema donde un proceso *parent* crea un *child* y el child crea un *grandchild*. El *grandchild* debe imprimir **"Soy usando el mejor "**,  luego dormir por 60 segundos; una vez pasado el minuto avisar al child que se despertó usando *pipes* y por último colgarse con un **while(TRUE);**. Al llegar al punto de cuelgue y recibir el mensaje por parte del grandchild, el child debe matarlo y hacer un `exit()`. Por último el parent espera a que el child termine e imprime **"Mi hijo querido se ha ido"** y termina.

a) Escribir un programa (en psendocódigo) que se comporte como el sistema descrito, utilizando las syscalls necesarias. Dado que se trata de pseudocódigo, no es necesario ser estricto con los parámetros y los valores de retorno de los syscalls, aunque sí respetar su espíritu.

b) Describir en qué estado queda cada uno de los procesos involucrados luego de la ejecución de cada syscall.

### 2.A

```c
void grandchild(int pipefd[2]) {
	int desperte = 0;
	close(pipe[READ]);
	
	printf("Soy el mejor nieto");
	sleep_for_seconds(60);
	
	write(pipe[WRITE], &desperte, sizeof(int));
	close(pipe[WRITE]);
	
	while(TRUE) {}
}

void child() {
	int desperto_hijo;
	int pipefd[2];
	pipe(pipefd);
	
	pid_t pidGrandchild = fork();
	
	if (pidGrandchild == 0) {
		grandchild(pipefd);
	}
	
	close(pipefd[WRITE]);
	read(pipefd[READ], &desperto_hijo, sizeof(int));
	close(pipefd[READ]);
	kill(SIGKILL, pidGrandchild);	
}

int main() {
	pid_t pidChild = fork();
	
	if (pidChild == 0) {
		child();
		exit(EXIT_SUCCESS);
	}
	
	wait_for_pid(pidChild);
	printf("Mi hijo querido se ha ido\n");
	
	return EXIT_SUCCESS;
}
```

### 2.B

Cuando el padre hace la syscall `wait_for_pid()`, se queda en estado BLOCKED hasta que termine el proceso pasado por parámetro, es decir, hasta recibir el SIGCHLD del proceso mencionado.
Luego del primer `fork()`, se comparte la memoria de padre a hijo, y de hijo a nieto después (aunque acá ya difiere de padre a nieto), pues fork() clona el proceso con su memoria.
Por otro lado, el proceso hijo se queda BLOCKED tras hacer `read()`, pues está esperando a que alguien escriba en ese pipe la cantidad de bytes pasadas por parámetro para poder seguir su ejecución, cosa que ocurre una vez que grandchild despierta y avisa al padre de esto antes de trabarse.
El grandchild en ese `sleep()` queda en estado BLOCKED por los 60 segundos que dura el mismo.
El proceso grandchild luego de quedar trabado en el `while (TRUE)`, oscila entre los estados RUNNING y READY por parte del scheduler, y luego recibe el SIGKILL del child, terminando automáticamente, pues SIGKILL termina el proceso instantáneamente, o espera a que el Reaper de systemd/init lo termine, a diferencia de SIGTERM que da un fin ordenado.
Por último, una vez que termina el child, el padre vuelve a correr tras recibir el SIGCHLD mencionado y termina (TERMINATED) .

a) Indicar qué file descriptors son utilizados y si vienen definidos por sistema (stdin, stdout, stderr)

### 3.A

Los file descriptors que se utilizan son:

- `0`, que apunta al stdin definido por el sistema, para que el usuario haga el input en por ejemplo
  `read(0, "anda\n", 1024)`
- `1`, apunta al stdout definido por el sistema. Se usa para enviar mensajes al usuario como por ejemplo en `write(1, "LLEGAMOS\n", 9)`.
- `3`, `4`, que son los file descriptors que apuntan a un pipe creado por los programas. Estos se usan para comunicarse entre ambos
  procesos, siendo 3 el extremo de lectura y 4 el de escritura. Se usan por ejemplo en: `read (3, <unfinished...>` y `write(4, "anda\n", 5)`.
- `5`, `6`, son otros file descriptors que apuntan a otro pipe de los programas.

### 3.B

Este es un progrma interactivo. Veamos por ejemplo como el prooceso 4673 queda bloqueado frecuentemente esperando a que el proceso 4672 le envíe
un mensaje enviado por el usuario. Es decir, se queda esperando E/S, y con mucha frecuencia. Lo mismo ocurre en 4672 al esperar la entrada al usuario por stdin.

### 3.C

```c
enum { READ, WRITE };

int pipePPCP[2]; // parent->child
int pipeCPPP[2]; // child->parent

int main() {
  pipe(pipePPCP);
  pipe(pipeCPPP);
  
  pid_t pidc = fork();

  if (pidc == 0) {
    close(pipePPCP[WRITE]);
    close(pipeCPPP[READ]);
    char buf_respuesta[256];
    for (;;) {
      read(pipePPCP[READ], buf_respuesta, 256);

      if (strncmp(buf_respuesta, "IR\n", 3) == 0) {
        write(pipeCPPP[WRITE], "YENDO\0", 6);
        break;
      }

      write(pipeCPPP[WRITE], "MENSAJE ERRONEO\0", 16);
    }
    sleep(5);
    exit(EXIT_SUCCESS);
  }

  close(pipePPCP[READ]);
  close(pipeCPPP[WRITE]);

  char buf_envio[1024];
  char buf_respuesta[1024];

  for (;;) {
    scanf("1023%s", buf_envio);
    write(pipePPCP[WRITE], buf_envio, 1024);
    read(pipeCPPP[READ], buf_respuesta, 1024);
    if (strncmp(buf_respuesta, "MENSAJE ERRONEO", 17) != 0)
      break;
  }

  waitpid(pidc);
  
  printf("LLEGAMOS\n");
  
  return EXIT_SUCCESS;
}
```
